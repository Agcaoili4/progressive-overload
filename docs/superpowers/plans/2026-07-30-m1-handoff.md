### 1. JWT validation has no test coverage (most important)

Setting `ValidateIssuer = false` in `src/ProgressiveOverload.Api/Program.cs` currently passes all
64 tests. The same blind spot exists for audience and lifetime. Only signature validation is
partially self-covering.

Add a `[Theory]` that mints access tokens with `JsonWebTokenHandler` using the same signing key
`ApiFactory` supplies, and asserts `GET /api/v1/me` returns 401 for each of: wrong issuer, wrong
audience, already-expired, tampered signature segment.

Then mutation-prove it: for `ValidateIssuer`, `ValidateAudience`, and `ValidateLifetime` in turn,
set the flag false, confirm the matching case FAILS, restore. Capture the real output. A test that
cannot be shown to fail is worth nothing here.

### 2. A comment documents a defence that does not exist

`src/ProgressiveOverload.Infrastructure/Auth/JwtTokenService.cs` (around line 30) states the
`stamp` claim is compared against the user's current `SecurityStamp` "on each request". Nothing
does that — `stamp` appears nowhere else in `src/`. So `SecurityStamp` rotation buys nothing today,
and the comment would convince a reader that a stolen access token dies when the password changes.
It survives its full 15 minutes.

Do **not** implement a per-request stamp check — that means a database read on every authenticated
request and defeats the point of a stateless access token. Rewrite the comment to say what is true:
the claim is carried so a future password-change or global-sign-out feature can use it, no check
exists yet, and the token stays valid until it expires.

**Carry forward:** when password change or global sign-out is built, it must revoke refresh-token
**families**, because the access token cannot be recalled before expiry.

### 3. Dead `.Include()` causing read amplification

`src/ProgressiveOverload.Application/Users/RecordBodyweight/RecordBodyweightHandler.cs` (~line 20)
does `.Include(u => u.BodyweightEntries)`, loading the user's entire weight history on every POST.
The backfill rule compares against the scalar `CurrentBodyweightAt`, and the explicit `.Add()`
makes the collection unnecessary. Remove it and confirm the bodyweight tests still pass, including
the backfill behaviour.

### 4. Second, unvalidated options binding

`src/ProgressiveOverload.Api/Program.cs` (~line 35) binds a second `JwtOptions` via
`.Get<JwtOptions>()!` instead of the `ValidateOnStart`-guarded `IOptions<JwtOptions>` registered in
`AddInfrastructure`. Harmless only because startup validation on the same section crashes first;
the `!` becomes a boot-time `NullReferenceException` if that section is ever renamed.

### 5. Comment style and a weak test

- 3–4 line `//` blocks inside methods in `ProfileEndpoints.cs`, `RecordBodyweightHandler.cs`,
  `Program.cs`, and `GetProfileHandler.cs`. The standard reserves `//` for one- or two-line notes;
  longer goes in a `/* */` block.
- `ProfileTests.cs` (~line 52) uses a bare `31`; express it as `User.MaxDisplayNameLength + 1`.
- `ProfileTests.cs` (~line 115) only asserts two user ids differ, which would pass even if an IDOR
  existed. Make it adversarial: have one user attempt to reach the other's data and assert failure.

## Deferred items for the final review

Recorded in the ledger with full context. Summary:

- Display-name validation duplicated in `User.cs` rather than sharing `ValidateCore`.
- `IPasswordHasher.Verify(string hash, string password)` — two same-typed params; transposing
  compiles and silently fails. Call sites use named arguments.
- `PasswordHasherAdapter` collapses `SuccessRehashNeeded` into `true`, so PBKDF2 parameter
  upgrades can never be applied.
- `RefreshToken.Revoke()` is dead in production; both revocation sites use `ExecuteUpdateAsync`.
- Google sign-in retry re-validates the token, so a transient JWKS failure turns a recoverable
  race into a hard failure.
- `PATCH /me` has replace semantics; omitting `bio` erases it. Product decision, left as is.
- No cleanup for expired `refresh_tokens` rows. Redeemed rows must be retained until `expires_at`
  so replay detection still works, so the table only grows. Fold a nightly delete into the
  background job that finalises weekly meets in Milestone 4.
- Refresh lifetime is sliding with no absolute cap. Deliberate for beta; revisit before Coach or
  Gym accounts, which hold third-party data.

## Process notes that saved real bugs

Worth keeping in any continuation:

- **Require mutation proof.** Three of the last five reviews found working code whose tests would
  have passed with the security property removed. "Tests pass" is not evidence; "the test fails
  when I break the property" is.
- **Report concurrency results per run configuration** — isolated single test, filtered class, full
  suite. One defect here was 100% reproducible in isolation and completely invisible warm.
- **Check for leftover mutation artifacts** whenever an agent dies mid-task. Two agents hit session
  limits during mutation testing, which deliberately breaks code before restoring it.
- **A verification command is itself code and can be wrong.** One mandated `grep` misfired against
  this repo's own comment style and flagged 64 comment lines as code.
